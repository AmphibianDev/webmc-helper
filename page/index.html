      What is on this machinechecking…

      WebMC is a Minecraft launcher whose interface is a web page, and whose promise is that the computer it runs on is borrowed rather than used: the game, the Java runtime and the helper are all deleted when the session ends.

      Why the page cannot launch anything

      A web page cannot start a program, read a file, or look inside /tmp. There is no API for it: WebAssembly and an in-page JVM are sandboxed, file:// gives an opaque origin that cannot even reach 127.0.0.1, a custom protocol handler and a browser extension both need an installer first, and a page has never been allowed to run a file it downloaded.

      That is not an oversight. The features that once did allow it — ActiveX controls, Java applets, Netscape plugins, Flash — were all removed precisely because a page being able to run native code is a security hole rather than a feature.

      Local Network Access, in current Chromium, makes the boundary explicit. Measured from a public page (this launcher on GitHub Pages) to the helper on 127.0.0.1:

      RouteResult
      fetch()Refused, or a permission prompt — “Permission was denied for this request to access the loopback address space.”
      an <iframe>Refused: the frame tree comes back with no child frame at all. A blocked frame still fires load, so that event proves nothing.
      a top-level navigationAllowed, with no prompt and no console error.

      Two things are worth telling an administrator, because they decide whether any of this works on a managed machine: the permission is called Local Network Access in Chromium's site settings, and one policy can refuse it outright — LocalNetworkAccessBlockedForUrls. Where that policy is set, nothing on a page can reach a local helper at all, and the helper's own page is the only route left.

      That last row is why this launcher behaves the way it does: the GitHub page cannot drive the helper, so it hands the tab to the helper's own page the moment it loads, which is allowed to talk to it — same origin, no prompt.

      What the helper does, step by step

      1. One staging directory. Everything goes there and nowhere else: a Python runtime if the machine has none, the helper, and later the game.
      2. A Java runtime, found or fetched. The version's own metadata says which Java it needs (javaVersion.majorVersion), and if this machine has nothing suitable the runtime is fetched into the staging directory and dies with it.
      3. The game, from Mojang. Client, the version's own libraries and the assets, every file verified against its published SHA-1, downloaded in parallel.
      4. The loader and your mods. Fabric's profile from Fabric's own metadata; your jars from this browser's storage, or fetched from Modrinth for the version you picked.
      5. The real client starts. An ordinary java …KnotClient process, with a normal window, exactly as any launcher would run it.
      6. You watch it here. The client's own output, streamed live into the log at the bottom of the window — which is why a crash is readable instead of mysterious.
      7. When it exits — closed, crashed, or stopped from here — the helper collects saves, logs, screenshots, configuration and crash reports into one zip.
      8. This page takes that zip into browser storage, and tells the helper to delete the sandbox. Nobody has to press anything: saving is automatic.
      9. Nothing is left for you to tidy up. If the page never comes back the helper deletes the sandbox itself after a deadline; if the helper is killed outright the next one finds the leftover by its owner file; if the machine reboots the OS clears its own temp directory. Settings → What is on this machine shows the inventory, and Leave nothing removes all of it.

      How you start itWhat remains when the session ends

      Installed — the double-click file Two small files: one Python file in Application Support, one launch agent so it starts at every login. The game is still deleted every session, and Leave nothing removes both.

      Where your world lives

      In this browser, under this page's origin. It is never uploaded, and there is no account. The consequence worth knowing: storage belongs to an origin, so the hosted page and the helper's page are different stores. That is exactly why the hosted page hands the tab over on arrival instead of running a session itself — one origin, one world, no surprises.

      Networks that block things

      The relay is one setting and it carries everything. Switched on, every download and every connection the game itself makes — joining a server, authenticating, fetching skins — travels inside ordinary HTTPS to the relay, which does the fetching and the dialling from outside the network that is blocking you. It is a Cloudflare Worker; two of them are deployed and built into the helper, so nobody has to run a command or make an account.

      What is blockedWhat to do
      Mojang is unreachable Nothing: on Automatic the relay fetches for you over ordinary HTTPS and caches what it fetched at the edge. A network that blocks Mojang is exactly what it exists for.
      Minecraft servers are unreachable (only 443 gets out) Also nothing, for the same reason: the game's connections ride inside the relay too. Put the server in Join this server and the client joins it automatically. The relay refuses any session that does not begin with a Minecraft handshake, because a relay that dialled any port for any bytes would be a port scanner.
      The relay's own hostname is blocked It is asked for through a proxy you already run, if there is one, and there are two hostnames to try. If neither answers you get a direct connection rather than an error.
      Servers that refuse datacenter addresses The relay dials from a datacenter, and some servers refuse those. That is the server's choice and no relay can change it — try another server, or Never and a proxy of your own.
      A program you did not write is blocked Nothing here changes that. AppLocker, WDAC, MDM, screen-time and parental controls are enforced by the operating system, and no launcher can get around them. On such a machine the only thing that runs is a launcher that installs nothing at all: the browser tier.

      More than one window

      Every PLAY is its own session, with its own sandbox, its own Java process and its own log. Two windows can run at once, including two different versions, and stopping one does not touch the other. Each finished session is stored and each deletes its own sandbox.

      Mod loaders

      LoaderState
      FabricWorks, for any version Fabric supports: mods are loaded at play time by a real JVM, from jars you dropped here or from Modrinth.
      Forge, NeoForgeNot supported yet: their builds resolve and their libraries download, but neither ships a usable client jar — their installer runs a patching step over Mojang's jar and their bootstrap refuses to start without it. Asking for one is refused with that explanation rather than half-launched.

      SymptomCause and answer
      Nothing happens when you press PLAY No helper is running. The status panel offers the Shortcut, the download, or the link to the helper's own page.
      “no helper” although it is running This browser blocked the request: use the helper's own page, or allow Local Network Access for this site.
      A launch fails with Failed to connect to Mojang The network blocks it. Leave the relay on Automatic.

      A crash Read the log, or take the session zip: it holds the client's own log and any crash report. Copy diagnostics puts everything worth pasting on your clipboard.

      How this works

      Minecraft never becomes a web app here. A helper on this machine downloads the real client and the Java runtime into one directory under /tmp, starts it with Fabric, and when the session ends it hands the saves to your browser and deletes the directory.

      This page cannot start a program, read a file, or see /tmp — the helper does that part. Documentation in the tabs above has the long version.
